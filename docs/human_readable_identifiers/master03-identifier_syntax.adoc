= Identifier Syntax

An HRID consists of two logical parts: an identifier of the reference model class on which the artefact is based (the `hrid_root`), and a version identifier. The grammar is as follows.

[source, ebnf]
--------
    hrid                    =   namespaced_hrid | local_hrid ;
    namespaced_hrid         =   namespace '::' local_hrid ;
    local_hrid              =   hrid_root '.v' version_id ;
    hrid_root               =   qualified_rm_class_name '.' concept_id ;
    qualified_rm_class_name =   rm_publisher '-' rm_closure '-' rm_class ;

    namespace               =   V_REVERSE_DOMAIN_NAME ;   (* IETF RFCs 1035, 1123, 2181 *)
    rm_publisher            =   V_ALPHANUMERIC_NAME ;
    rm_closure              =   V_ALPHANUMERIC_NAME ;
    rm_class                =   V_ALPHANUMERIC_NAME ;
    concept_id              =   V_SEGMENTED_ALPHANUMERIC_NAME ;

    V_ALPHANUMERIC_NAME           =   ? [a-zA-Z][a-zA-Z0-9_]+ ? ;   (* regex *)
    V_SEGMENTED_ALPHANUMERIC_NAME =   ? [a-zA-Z][a-zA-Z0-9_-]+ ? ;  (* allows hyphens *)
--------

The version identifier (`version_id`) is defined in <<Version Numbering>>.

The field meanings are as follows:

* `namespace`: reverse domain name of the publishing organisation, e.g. `org.openehr`, `uk.nhs`, `edu.nci`;
* `rm_publisher`: identifier of the organisation originating the reference model on which the artefact is based, e.g. `openEHR`, `ISO`;
* `rm_closure`: identifier of the reference model top-level package closure from which the focal class is reachable, e.g. `EHR`, `ISO13606`; a class may be reachable from more than one closure, but a given artefact is designed for exactly one;
* `rm_class`: name of the reference model class on which the artefact is based, e.g. `OBSERVATION`, `ENTRY`;
* `concept_id`: an ontological identifier for the concept represented by the artefact (see below).

The `hrid_root` thus takes forms such as `openEHR-EHR-OBSERVATION.bp_measurement` or `ISO-ISO13606-ENTRY.bp_measurement`.

The notion of _closure_ is that of a top-level package from which the focal class can be reached. A given class may be reachable from more than one closure, but an artefact of that class is designed for only one of them. For example, the openEHR `CLUSTER` class is reachable from both the `EHR` and `demographic` closures, yet a `CLUSTER` archetype such as `openEHR-EHR-CLUSTER.physical_examination` is meaningful only within `EHR` data; a tool can use the closure to ensure that such an artefact is never attached to a demographic information item.

== Need for the Reference Model Class Name

In principle the qualified reference model class name (`qualified_rm_class_name`) would not be needed if concept identifiers never clashed. In practice, an appropriate name for a data-level concept can also be a reasonable name for a higher-level container of the same data - for example `lab_result` is a plausible `concept_id` for an `OBSERVATION` (or ISO 13606 `ENTRY`) capturing a laboratory result, yet `lab_result` might equally be chosen for a `COMPOSITION` designed to contain such results. In the absence of a global concept-identifier authority, including the qualified reference model class name guards against such clashes and lets tools ensure that an artefact is only applied to a suitable information structure.

== Concept Identifier

The `concept_id` is a 'short' ontological identifier (known in ADL 1.4 as the 'concept' or 'domain concept'), historically a natural-language mnemonic such as `bp_measurement`.

The concept identifier is part of the human-readable identifier because it is human-readable and facilitates debugging of systems whose data carry these identifiers. Purely ad hoc assignment does not scale, so the authoritative form of a concept identifier should be a 'short identifier' - a synonym for a full node identifier - drawn from an ontology corresponding to the `namespace` of the identifier and maintained by the custodian organisation or a higher authority. This specification does not define such an ontology; it requires only that concept identifiers be unique within a namespace.

NOTE: In legacy (ADL 1.4) identifiers, the concept part could encode a specialisation hierarchy as hyphen-separated segments, e.g. `problem-diagnosis`. The `'-'` character remains permitted within `concept_id`, but carries no structural significance in this specification; the level of specialisation of an artefact can no longer be inferred from its identifier.
